## 背景与实测数据

诊断见 `proposal.md`。要点：**核心的那 1 秒无法从插件侧消除**（DSH 对 patch 层的每次真实变更都会重应用整棵配置树），但**触发次数**和**用户可感知性**都在本插件的控制范围内。

实测（本机 `web` profile）：

| 场景 | 宿主事件循环最大阻塞 | 备注 |
|---|---|---|
| 真实开关（关） | 1184 ms | POST 往返仅 30 ms |
| 真实开关（开） | 797 ms | POST 往返 19 ms |
| 真实开关 ×2（另一轮） | 681 ms / 1021 ms | SSE `/plugins/events` 全程未断 |
| 写入完全相同字节 | 0（max 71 ms） | 配置未变 → 核心短路 |
| 无任何开关的 180 秒 | 1459 ms（1 次） | 同类阻塞也会自发出现 |

## 设计决策

### R1：合并窗口放在主机半，而不是客户端

客户端去抖只能减少「请求数」，做不到减少「写入数」。要让 N 次点击只写一次文件，合并必须发生在写入点，即主机半的 `/set-enabled` 处理里。因此客户端保持「点一下就发一个请求」，由主机合并。

### R2：待写状态用「意图列表」而不是「副本行数组」

待写状态存为 `{id, name, enabled}` 的意图列表（对同一行去重、后写覆盖），落盘时才**重新读取磁盘行**再逐个套用 `upsertManaged`。这样窗口期内若有人（用户手工编辑、其它工具）改了 patch 文件，也不会被我们用陈旧副本覆盖。

### R3：响应即时反映意图（服务端叠加，不做客户端乐观状态）

`snapshot()` 在 `deriveStates` 之前把意图叠加到磁盘行上，于是点击后的响应已经带目标状态，面板开关在 ~30 ms 内到目标位置。既然响应足够快，就不需要客户端维护「乐观副本 + 回滚」那套状态机。

### R4：默认去抖 400 ms

用户连点的间隔通常 150–400 ms；400 ms 能覆盖「手快连点」，又把「插件实际生效」的延迟控制在可感知阈值边缘。常量 `INTENT_DEBOUNCE_MS` 放在 `host-core.js`（可单测），不做配置项（不引入 patch 文件配置面）。

### R5：「正在应用」的判定条件 = pendingWrites 为 0 **且** 宿主往返恢复正常

只探测往返时延会漏判：写请求返回时可能还在去抖窗口内（宿主尚未开始重应用，探测必然很快）。因此 `/status` 暴露 `pendingWrites`，客户端在「还有待写」或「探测往返超过阈值」期间持续显示「正在应用」，两者都满足才撤下提示。

### R6：不锁死面板

若在 `applying` 期间禁用其它开关，用户想连改 3 个插件就得串行等 3 秒，正好抵消 R1 的收益。因此 `applying` 只做提示，不禁用开关；重复点击由主机合并（同行的再次点击覆盖同一意图，不产生额外写入）。

### R7：失败与退出路径

- 落盘失败：记录 `HOST_DIAG.lastFlushError`，响应里已给出的意图状态与磁盘不一致 → 下次 `/list` 以磁盘为准，面板显示错误。
- 退出（`ctx.effect` 清理）：若仍有待写意图，用同步路径（`requireProfileYaml` + `readPatchRows` + `upsertManaged` + `writePatchRows`）尽力落盘；失败则放弃并保留磁盘原状，绝不写半个文件（`writePatchRows` 是整文件覆盖写）。
- 移除/迁移：动作前先 `flushPending()`，避免更早的意图在移除之后又被写回。

## 风险与回滚

- **风险**：把「立即持久化」改成「最多延迟 400 ms 持久化」，窗口内进程被强杀（KILL）会丢失该次意图。缓解：正常退出走 R7 同步落盘；文档中写明该窗口。
- **风险**：意图叠加期间若用户手工把 patch 文件改成与意图冲突的状态，以最后一次落盘为准（落盘会重新读盘再套用意图）。文档写明。
- **回滚**：单文件改动（`host-core.js` / `index.js` / `client.js`），`git revert` 即回到「立即写入」；不需要动 profile 或子插件。

## 备选方案（已否决）

- **改核心**：让 DSH 的 patch 重应用不再独占事件循环（增量应用／分片／只重挂改动项）——超出本插件范围；本次只在 `docs/knowledge` 记录该结论，供上游参考。
- **幂等写保护（状态未变则不写）**：实测核心对未变配置已短路，收益为零。
- **直接调用 loader API 生效 + 延迟写文件**：总代价不变（文件写入终究触发一次重应用），只是把卡顿挪到不可预期的时刻，体验更差。
- **在 `applying` 期间锁住面板**：见 R6，反而放大代价。
